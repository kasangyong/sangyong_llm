# sangyong_llm 설계 문서

작성일: 2026-08-13

## 목표와 범위

파이썬 코드를 생성하는 디코더 전용 트랜스포머를 **밑바닥부터 직접 구현**한다.

PyTorch에서 빌려 쓰는 것은 세 가지뿐이다.

- 텐서 연산과 autograd
- CUDA 백엔드
- `F.scaled_dot_product_attention` (융합 어텐션 커널)

토크나이저, 어텐션 수식, 위치 인코딩, 정규화, 블록 배선, 학습 루프,
데이터 파이프라인, 평가 채점기는 전부 직접 작성했다. HuggingFace
`transformers`, `tokenizers`, `datasets`는 쓰지 않는다.

### 범위 밖 (하드웨어 상한)

| 모델 크기 | 학습 토큰 | 추정 시간 (RTX 4050 6GB) |
|---|---|---|
| 53M | 1B | 약 17시간 |
| 124M | 2.5B | 약 4일 |
| 1B | 20B | 약 9개월, **6GB에 안 들어감** |

Claude Opus 5급(1e26~1e27 FLOPs, 학습비 $200M~500M)은 이 하드웨어의
범위 밖이다. 구현 능력의 문제가 아니라 물리적 상한이다.

## 하드웨어와 환경

- GPU: NVIDIA RTX 4050 Laptop, VRAM 6.00GB, sm_89
- Python 3.12.13 (uv 관리) — 3.14에는 CUDA 휠이 없어 별도 venv를 만들었다
- PyTorch 2.11.0+cu128
- CPU 20코어 (데이터 파이프라인 병렬화에 사용)

## 아키텍처

Llama 계열 구성. `model/transformer.py`.

| 항목 | 값 |
|---|---|
| d_model | 640 |
| n_layers | 10 |
| n_heads | 10 (head_dim 64) |
| n_kv_heads | 2 (GQA) |
| FFN | SwiGLU, d_ff 1728 |
| 위치 인코딩 | RoPE (theta 10000) |
| 정규화 | RMSNorm, pre-norm |
| vocab | 16,384 |
| context | 1,024 |
| 임베딩 | 입출력 공유 |
| **파라미터** | **53,507,200** (비임베딩 43,021,440) |

### 설계 판단 근거

- **GQA (KV 헤드 2개)**: KV 캐시가 생성 시 VRAM을 잡아먹는다. 질의 헤드는
  10개로 유지하고 KV만 2개로 줄여 캐시를 5분의 1로 만든다.
- **RMSNorm을 float32로 계산**: bf16으로 제곱합을 구하면 정밀도가 무너진다.
  정규화만 float32로 올리고 결과를 다시 내린다.
- **잔차 투영 축소 초기화**: `wo`, `w_down`을 `0.02/sqrt(2*n_layers)`로
  초기화한다. 안 하면 층을 쌓을수록 잔차 분산이 누적돼 학습 초반이 불안정하다.
- **KV 캐시가 찬 상태의 다중 질의는 거부**: `F.sdpa`의 `is_causal`은
  마스크를 좌상단 기준으로 정렬하므로 `kv_len > q_len`인 경우 조용히 틀린
  답을 낸다. 지원하지 않고 `ValueError`를 던진다.

## 토크나이저

바이트 단위 BPE. `tokenizer/bpe.py`.

- 기본 어휘가 0~255 전체 바이트 → **미등록 토큰(OOV)이 원리적으로 없다**
- 사전 분할은 코드에 맞춰 식별자/숫자/기호/들여쓰기를 각각 끊는다
- 학습은 조각 빈도 사전 위에서 돌리고, 병합 시 영향받은 단어의 쌍 카운트만
  증분 갱신한다 (전체 재집계 없음)

### 어휘 크기 불변 조건

작은 코퍼스에서 병합할 쌍이 소진되면 요청한 `vocab_size`를 못 채운다.
이때 **조용히 줄어들면 모델 임베딩 크기와 어긋나 나중에 터진다.** 남는
자리를 예약 토큰으로 채워 `vocab_size`를 불변으로 유지하고, 경고를 출력한다.
예약 토큰은 학습 데이터에 나타나지 않으며 디코딩 시 무시된다.

### 필터

`data/prepare.py filter`

1. 라이선스: `mit`, `apache-2.0`, `bsd-3-clause`, `bsd-2-clause`, `isc`,
   `unlicense`, `cc0-1.0`, `0bsd`, `zlib`만. GPL/AGPL/LGPL/MPL/EPL 제외
2. 자동 생성 파일 제외
3. 크기 64B ~ 200KB
4. `alpha_frac >= 0.25`, `line_max <= 1000` (데이터 덩어리 배제)
5. **`ast.parse` 통과** — 파이썬이라서 "유효한 코드인가"를 공짜로 확실하게
   판정할 수 있다. 휴리스틱보다 강력하고, 파이썬 2 전용 파일도 함께 걸러진다
6. 데이터셋 `hash` 기준 전역 중복 제거

실측(8샤드): 800,000개 중 419,773개 유지(52.5%), 3.63GB.
탈락은 라이선스 316,329 + 문법 63,095 + 크기 803.
해시 기준 전역 중복은 0개 — codeparrot-clean이 이미 중복 제거되었다는 설명이
실제로 맞았다.

### 토큰화

`data/prepare.py tokenize`. 멀티프로세싱(워커 수 조절 가능). 문서 경계에
`<|endoftext|>`를 넣고 uint16으로 저장한다 (vocab 16,384 < 65,536).
500문서마다 1개를 검증셋으로 뺀다.

실측 결과:

| 항목 | 값 |
|---|---|
| train.bin | 1,027,146,559 토큰 (1,959 MB) |
| val.bin | 2,103,160 토큰 (4 MB) |
| 합계 | 1,029,249,719 토큰 |

53M 모델의 Chinchilla 최적 토큰 수(약 1.07B)와 거의 일치한다.

토크나이저 실측: 병합 16,127개(예약 0), held-out 압축률 3.763 바이트/토큰,
held-out 3,000문서 28.3MB 왕복 무손실.

## 학습

`train/train.py`

| 항목 | 값 |
|---|---|
| 옵티마이저 | AdamW (β 0.9/0.95), fused |
| weight decay | 0.1 — **2차원 이상 파라미터에만** |
| lr | 6e-4, 워밍업 200스텝 후 코사인 감쇠 → 6e-5 |
| grad clip | 1.0 |
| 정밀도 | bf16 autocast |
| 유효 배치 | 2 × 64(누적) × 1024 = 131,072 토큰/스텝 |

### VRAM: Windows에서 OOM은 신호가 아니다

WDDM은 VRAM이 모자라도 OOM을 내지 않는다. 드라이버가 조용히 시스템 RAM으로
흘려보내기 때문에 "돌긴 도는데 10배 이상 느린" 상태가 된다. 따라서
`try/except OutOfMemoryError`로 배치 크기를 정하면 안 된다.

`scripts/probe_vram.py`는 최대 할당량이 안전선(전체 VRAM의 85%)을 넘는지와
스텝 시간이 튀는지를 함께 본다. 실측:

| batch | peak | 초/스텝 | 토큰/초 | 판정 |
|---|---|---|---|---|
| 1 | 1.66GB | 0.660 | 1,552 | OK |
| 2 | 2.59GB | 1.284 | 1,595 | OK (최적) |
| 4 | 4.45GB | 26.008 | 157 | 스텝 시간 20배 급증 |
| 6 | 6.30GB | - | - | 안전선 초과, 시스템 RAM 유출 |

**주의**: 이 측정은 GPU를 다른 작업(PPO 강화학습, GPU 98% 점유, VRAM 4GB)과
공유하는 상태에서 나왔다. 클럭도 3105MHz 중 630~900MHz로 눌려 있었다.
GPU가 비면 반드시 다시 측정하고 `batch_size`를 올릴 것. 위 수치로 추정한
1B 토큰 학습 174시간은 상한이며, 전용 GPU에서는 크게 줄어든다.

- 기울기 누적 시 `loss / grad_accum`으로 나눠 통짜 배치와 등가를 유지한다
- 체크포인트는 임시 파일에 쓴 뒤 교체한다 (저장 중 중단에도 기존 파일 보존)
- `latest.pt`(재개용) / `best.pt`(검증 손실 최소) 분리
- `BinDataset.close()` — Windows는 memmap이 열린 동안 파일을 잠근다.
  학습 중 데이터 교체가 막히지 않도록 명시적으로 놓아준다

## 평가

`eval/harness.py`

1. **문법 유효율**: 생성 결과의 `ast.parse` 통과 비율
2. **pass@k**: 문제별 k개 생성 후 하나라도 테스트를 통과하는 비율

### 채점기 신뢰성

채점기부터 검증했다. 정답 10개는 통과하고 일부러 틀린 답 10개는 떨어져야
한다. 후자가 통과하면 테스트가 허술한 것이다.

**종료코드만 보면 안 된다.** 생성 코드가 `sys.exit(0)`이나 `os._exit(0)`을
부르면 테스트를 건너뛰고 0을 반환한다. 테스트 뒤에 센티넬을 출력하게 하고
그것이 실제로 찍혔는지까지 확인한다 (`reason='early_exit'`).

격리는 별도 프로세스 + 타임아웃 수준이다. 컨테이너나 seccomp를 쓴 진짜
샌드박스는 아니며, 자기 모델이 자기 기계에서 만든 코드라는 전제에 기댄다.

## 검증 원칙

각 단계는 **먼저 깨뜨려보고**, 통과한 것만 다음으로 넘긴다. 판정은
위험/보통/통과 3단계이며 통과만 진행한다.

| 단계 | 검증 | 결과 |
|---|---|---|
| 0. 환경 | 9항목 (GPU 행렬곱 정확도, bf16, GQA SDPA, VRAM) | 9/9 |
| 1. 토크나이저 | 13항목 (적대적 입력 28종, 무작위 유니코드 1000건) | 13/13 |
| 2. 모델 | 14항목 (인과 누설, RoPE 상대위치, KV 캐시 등가) | 14/14 |
| 3. 학습 루프 | 8항목 (누적 등가, 단일배치 과적합, 재개 궤적) | 8/8 |
| 평가 하네스 | 12항목 (정답/오답 판별, 우회 차단) | 12/12 |

### 특히 중요한 검증

- **인과 마스크 누설**: 미래 토큰을 바꿔도 과거 위치 출력이 변하지 않아야
  한다. 여기가 뚫리면 손실은 예쁘게 떨어지지만 생성은 전혀 안 된다.
  손실 곡선만 봐서는 절대 못 잡는다. 실측 최대차 0.00e+00
- **KV 캐시 등가성**: 캐시 경로와 통짜 forward가 일치해야 한다. 캐시 버그는
  학습 지표에 안 나타나고 생성 품질만 망가뜨린다. 실측 최대차 2.38e-07
- **중단/재개 궤적**: 옵티마이저 모멘텀을 빠뜨리는 버그는 이 테스트만이
  잡는다. 실측 손실 최대차 0.00e+00
- **단일 배치 과적합**: 모델·옵티마이저·손실이 실제로 연결됐는지 확인.
  loss 5.609 → 0.00000

## 실행 순서

```bash
.venv/Scripts/python.exe scripts/verify_env.py
.venv/Scripts/python.exe data/download.py --shards 8
.venv/Scripts/python.exe data/prepare.py filter
.venv/Scripts/python.exe data/prepare.py tokenizer --sample-mb 100
.venv/Scripts/python.exe data/prepare.py tokenize
.venv/Scripts/python.exe train/train.py
.venv/Scripts/python.exe eval/harness.py --ckpt checkpoints/best.pt
```
