=== sangyong_llm 진행 기록 ===

## 2026-08-13

파이썬 코드 생성용 53M 트랜스포머를 밑바닥부터 구현하는 프로젝트를 시작해
프리트레이닝 직전까지 완료했다. PyTorch는 텐서/autograd/CUDA/융합 어텐션
커널만 쓰고, 토크나이저·어텐션·RoPE·RMSNorm·학습 루프·데이터 파이프라인·평가
채점기는 전부 직접 작성했다.

각 단계는 먼저 깨뜨려보고 통과한 것만 다음으로 넘기는 방식으로 진행했다.
누적 56개 검증 항목이 통과 상태다.

### 완료

- 0단계 환경 (9/9): Python 3.14에 CUDA 휠이 없어 3.12 venv를 별도로 만들고
  torch 2.11.0+cu128 설치. GPU 행렬곱이 CPU와 일치(6.1e-05), bf16, GQA SDPA,
  가용 VRAM 4.90GB 확인.
- 1단계 토크나이저 (13/13): 바이트 단위 BPE 직접 구현. 적대적 입력 28종과
  무작위 유니코드 1000건 왕복 무손실.
- 2단계 모델 (14/14): RoPE/RMSNorm/GQA/SwiGLU. 파라미터 53,507,200개로 설계
  손계산과 정확히 일치. 인과 누설 최대차 0.00e+00.
- 3단계 학습 루프 (8/8): AdamW, 코사인 스케줄, bf16, 체크포인트/재개.
  단일 배치 과적합 loss 5.609 -> 0.00000. 재개 궤적 차이 0.00e+00.
- 평가 하네스 (12/12): 정답 10개 통과 / 오답 10개 탈락. sys.exit(0),
  os._exit(0) 우회 차단.
- 데이터: codeparrot-clean 8샤드 필터 완료. 419,773 문서 / 3.63GB
  (유지율 52.5%).

### 잡은 버그

1. 토크나이저 어휘 크기가 조용히 줄어드는 문제. 작은 코퍼스에서 병합이
   소진되면 vocab_size=1000을 요청해도 400이 나왔다. 모델 임베딩과 어긋나는
   순간 터진다. 예약 토큰으로 크기를 불변으로 만들고 경고를 붙였다.
2. BinDataset이 memmap을 안 닫아 Windows에서 파일이 잠기는 문제. 학습 중
   데이터 교체가 막힌다. close()와 컨텍스트 매니저를 추가했다.
3. 채점기가 sys.exit(0)에 속는 문제. 종료코드 0만 보면 테스트를 건너뛴
   코드가 통과로 잡힌다. 센티넬 출력 확인을 추가했다.

### GPU 경합 이슈 (해소됨)

사용자의 PPO 강화학습(sim.train.ppo, 16384 env)이 GPU를 98% 점유하고
있어서 클럭이 3105MHz 중 645MHz로 눌려 있었다. 속도 측정이 전부 오염됐다.
사용자 판단으로 PPO 종료를 기다렸고, 종료 후 클럭이 2160~2385MHz로 복귀했다.

### VRAM 실측 (중요)

Windows WDDM은 VRAM을 넘겨도 OOM을 내지 않고 시스템 RAM으로 조용히
흘려보낸다. 그래서 "동작은 하는데 20배 느린" 상태가 된다. OOM 여부로
배치 크기를 정하면 안 되고, 최대 할당량이 안전선(전체의 85%)을 넘는지와
스텝 시간이 튀는지를 함께 봐야 한다. 결론: batch_size 4 (peak 4.45GB),
기울기 누적 32 -> 유효 배치 131,072 토큰/스텝.

### 진행 중

53M 본 프리트레이닝 시작. 7,800스텝 = 약 1.02B 토큰 = 1에포크.
초기 loss 9.8597 (ln(16384)=9.70과 일치), VRAM 4.26GB, GPU 100% 가동.

## 2026-08-14 — 검색/툴 레이어

tools/protocol.py, tools/search.py, tools/pipeline.py, tests/test_tools.py를
추가했다(40/40 통과). 토크나이저와 학습 중인 체크포인트는 건드리지 않았다.
툴 호출 포맷은 특수 토큰 없이 한 줄짜리 일반 텍스트 마커 `### 검색: <질의>`로
정했다. 닫을 것이 없어 53M 모델이 배우기 쉽고 기존 `### 지시:` 형태와 같은
모양이다. 파서는 줄 시작 마커만 인정하고 코드블록/삼중따옴표 구간은
마스킹한다. 잘린 호출과 빈 질의는 무시하되 ParseIssue로 보고한다.
검색은 Brave/Tavily/Serper 세 제공자를 SearchResult로 정규화하고, HTTP는
주입 가능한 fetch로 빼서 테스트에서 네트워크를 쓰지 않는다. 키 없음 /
429 / 401 / 타임아웃 / 네트워크 / 깨진 JSON을 각각 다른 예외로 구분한다.
컨텍스트 포맷터에서 실제 문제를 하나 잡았다: 한국어 스니펫이 이 토크나이저
에서 문자당 토큰 비용이 높아, 300자 스니펫 하나가 240토큰 예산을 통째로
먹고 포함 0개/생략 5개가 나왔다. 결과 하나당 예산 상한(기본 budget/3)을
두고 스니펫만 줄이되 제목+url 머리줄은 남기도록 고쳤다.
참고: 한글 마커는 9~15토큰, 같은 뜻의 ASCII 마커는 4~5토큰이다. SFT 시작
전이라면 마커를 ASCII로 바꾸는 것이 컨텍스트 예산상 유리하다(상수 한 줄).

## 2026-08-18 — ASCII 마커 전환 + 전체 코퍼스로 재학습

### 1B 토큰 학습의 결말

iter 250에서 중단했다. 죽은 게 아니라 노트북이 4일간 절전에 들어갔다가

### ASCII 마커 전환

실측: "### 검색:" 9토큰 -> "### Search:" 3토큰, "### 검색결과:" 15 -> 4,
"### 지시:" 9 -> 4, "### 코드:" 9 -> 3. 합계 51 -> 19토큰.
검색 한 라운드가 33 -> 12토큰이 된다. 컨텍스트가 1,024뿐이라 라운드마다
21토큰은 결과 스니펫 하나 분량이다.

전환하면서 테스트 설계 결함을 하나 고쳤다. 픽스처가 마커를 상수가 아니라
리터럴로 박아둬서, 상수를 바꾸자 파서 테스트 12개가 한꺼번에 실패했다.
증상이 "파서가 깨졌다"로 보여서 원인 찾는 데 시간이 든다. 픽스처-상수
일치를 먼저 검사하는 가드 테스트를 앞에 세웠고, 잘린 마커 테스트는
CALL_MARKER[:-2]로 파생시켜 다시는 어긋나지 않게 했다(리터럴 "### 검"은
마커가 바뀌자 더 이상 접두사가 아니게 되어 엉뚱하게 실패했다).

### 전체 코퍼스

codeparrot-clean 54샤드 전량. 8샤드에서 1.03B 토큰이 나왔으므로 약 6.9B
토큰이 예상된다. 53M 모델에는 Chinchilla 최적(1.07B)의 6.5배지만, 과학습은
현대 표준 관행이고 추론 비용이 그대로라 실사용에 유리하다. 사용자 판단으로
모델 크기는 53M을 유지한다.

토크나이저는 재학습하지 않는다. 100MB 표본에서 이미 압축률 3.763이 나왔고
16k vocab BPE는 표본을 키워도 병합이 거의 수렴한다. 재학습하면 CPU 한 시간을
쓰고 얻는 게 거의 없다.

## 2026-08-31 — V100 서버 이전, fp16 전환, 282M 결정

학습을 SSAFY GPU 서버(Tesla V100S-PCIE-32GB 10장 중 3번 1장)로 옮기기로
하고, 그 하드웨어에서 실제로 돌 수 있게 코드를 고쳤다. 커밋 3개.

### V100 실측에서 나온 것

fp32 13.2 / fp16 88.8 / bf16 10.0 TFLOPS. bf16이 fp32보다 느리다 —
sm_70에는 bf16 텐서코어가 없고 소프트웨어 에뮬레이션만 있기 때문이다.
그런데 torch.cuda.is_bf16_supported()는 V100에서도 True를 반환한다.
지원 여부만 보던 verify_env.py가 거짓 통과시키고 있었다.

또 최신 PyTorch(2.11+)는 Volta를 빌드 타겟에서 뺐다(최소 sm_75). README의
cu128을 깔면 "no kernel image is available"로 죽는다. sm_70이 들어 있는
마지막 조합은 torch 2.6.0 + cu124다.

### 고친 것

model/precision.py를 새로 만들어 compute capability로 dtype을 고른다
(sm_80 이상 bf16 / 미만 fp16). verify_env.py는 지원 여부가 아니라 실측
TFLOPS가 fp32보다 빠른지를 판정 근거로 쓴다.

fp16이라 GradScaler가 붙었다. 여기서 조용히 망가지는 지점을 먼저
재현했다 — 기울기 클리핑을 scaler.unscale_() 앞에 두면 스케일된 기울기를
자르게 되어 유효 학습률이 무너진다. 실측(scale 128, clip 1.0):

  unscale -> clip  보고 gnorm 0.2500  클리핑 후 실제 노름 0.2500
  clip -> unscale  보고 gnorm 31.999  클리핑 후 실제 노름 0.0078

보고 gnorm이 128배 부풀려지는 건 부수적이고 실제 기울기가 32배 축소된다.
손실 곡선에는 아무 징후가 없다. clip_and_step() 하나로 순서를 고정하고
회귀 테스트를 붙였다. 변이 주입으로 그 테스트가 실제로 잡는 것까지 확인했다.
fp16 손실 스케일은 체크포인트에 함께 저장한다.

### 모델 크기 결정

53M은 노트북 6GB 상한에서 역산한 값이라 32GB에서는 작다. 사용자 판단으로
282M + 54샤드 전량(약 6.6B 토큰)으로 간다. ModelConfig 기본값을 갈아끼우지
않고 PRESETS(53m/282m)로 뺐다 — 기본값을 바꾸면 --model 없이 돌린 학습과
명시한 학습이 서로 다른 모델이 되는데 체크포인트만 봐서는 구분이 안 된다.

  53m   53,507,200  d_model 640  10층  context 1024
  282m 282,641,408  d_model 1024 24층  context 2048

예상 시간 4.4~6.1일 (FLOPs/token = 6N + 6·L·T·d = 2.00G, 실효 22~35 TFLOPS
가정). 처음에 4.3일이라고 적었던 것은 어텐션 항을 빼먹은 값이라 정정했다.

train_detached.py를 POSIX에서도 쓸 수 있게 고쳤다(start_new_session /
signal 0 / SIGTERM). SERVER_SETUP이 서버에서 이걸 쓰라고 안내하는데
tasklist와 CREATE_NEW_PROCESS_GROUP은 Windows 전용이라 리눅스에서 죽었다.

검증: 8개 스위트 138항목 통과. fp16/bf16/fp32가 같은 지점으로 수렴
(53M 축소판 120스텝, loss 5.59 -> 0.0593/0.0590/0.0596, NaN 0, 스킵 0).

### 서버에서 진행 중

git pull -> verify_env -> run_tests -> download 54샤드 -> filter ->
tokenize -> probe_vram --model 282m -> train_detached start --model 282m.
tokenize는 재개가 안 되므로(출력을 "wb"로 연다) tmux 안에서 끝까지 돌려야
한다. data/prepare.py tokenizer는 절대 실행하지 않는다 — 어휘 16,384가
바뀌면 모든 체크포인트가 무용지물이 된다.

로컬 data/processed/train.bin은 2,677,510,268 토큰에서 중단된 상태로
남아 있다. 서버에서 전량을 새로 만들므로 이제 쓰지 않는다.

### 학습이 끝나면 (순서)

1. train_detached.py status로 "학습 종료" 확인, fp16 스킵 스텝 수 확인
2. 서버에서 sample.py로 먼저 생성해 본다. 손실은 떨어졌는데 생성이 안 되는
   경우가 있으므로 3.2GB를 내려받기 전에 확인한다
3. SFT를 서버에서 이어서 돌린다. 282M 학습은 가중치+기울기+Adam만 4.5GB라
   로컬 6GB에 안 들어간다. 추론은 0.6GB라 여유롭다
4. export_weights.py --half 후 로컬에서 scp로 pull (서버는 노트북에 접속
   못 한다). 서버 자원이 회수될 수 있으면 best.pt(3.2GB)도 함께 받아둔다
5. 로컬에서 eval/harness.py로 pass@k 측정

체크포인트는 git에 올리지 않는다. GitHub 파일 상한이 100MB이고 .gitignore가
이미 checkpoints/*를 막고 있다. 보관이 필요하면 GitHub Releases(파일당 2GB).

### 남은 작은 문제

export_weights.py --half이 임베딩 공유를 깨뜨린다. dtype 변환이 새 텐서를
만들어 tok_emb.weight와 lm_head.weight가 파일에 두 번 저장된다(실측: 고유
저장소 92 -> 93). 53M에서 20MB, 282M이면 약 34MB가 더 붙는다. 두 사본 값이
같고 로드 시 묶인 파라미터에 둘 다 쓰이므로 정확도에는 영향이 없다.
파일 크기만의 문제라 아직 안 고쳤다.

                  문법 유효율   pass@5   개별 샘플
  미학습 기준선        60.0%      0.0%     0/20
  282M (한글 프롬프트) 98.0%     40.0%    12/50

실패는 대부분 assert다 — 문법은 맞는데 답이 틀린다. 지시 튜닝 전 기반 모델이라

### 벤치마크 자체의 문제

eval/problems.py의 독스트링이 한국어인데 모델은 codeparrot-clean(영어/코드)만
봤다. 토큰 비용도 실측으로 4~7배다:

  "두 수를 더해 반환한다."          31토큰
  "Return the sum of two numbers."  7토큰

영어로 바꾸면 pass@5가 40% -> 60%로 오른다. 다만 10문제 k=5는 표본이 작아
2문제 차이는 분산일 수 있다(개별 샘플로는 24% -> 34%, n=50). 토큰 비용 쪽은
결정적이므로 벤치마크 프롬프트를 영어로 바꾸는 편이 맞다. 아직 안 바꿨다.

### 다음

SFT는 로컬에서 못 돌린다. 282M 학습은 가중치 1.13 + 기울기 1.13 + Adam 2.26 =
4.52GB라 6GB 카드에 활성값까지 안 들어간다(추론은 1.1GB라 여유). 서버 자원이

## 2026-09-18 (2) — 마무리: 내보내기 버그, 벤치마크 언어, 문서

서버 자원이 회수돼 SFT는 못 돌린다. 기반 모델을 최종 산출물로 두고 남은
것들을 정리했다.

### export_weights.py --half 수정

dtype 변환을 키마다 따로 하면 `.to()`가 새 저장소를 잡아 입출력 임베딩의
공유가 끊긴다. 같은 값이 파일에 두 번 들어가는데 정확도에는 영향이 없어서
파일 크기를 재보기 전에는 안 드러난다. 실측(53M): 저장소 92 -> 93,
102MB로 끝날 파일이 122MB. 초과분 20.0MB는 임베딩 10,485,760개 x 2바이트와
정확히 일치한다.

cast_state()로 빼고 저장소 뷰 기준으로 한 번만 변환해 공유를 유지한다.
tests/test_export.py를 9번째 스위트로 추가(5항목). 변이 주입으로 공유 검사와
파일 크기 검사가 둘 다 잡는 것을 확인했다 — 크기 임계값은 0.55로는 소형
모델에서 못 잡아 0.51로 조였다(정상 0.502, 버그 0.537).

282M 재내보내기: 1,078.3 MiB -> 539.3 MiB (정확히 50%, 공유 218/219 유지).

### 벤치마크 독스트링 영어로

eval/problems.py의 프롬프트 독스트링이 한국어였다. 모델은 영어/코드만 봤고
토크나이저가 한글을 거의 병합하지 않아 같은 뜻이 4~7배 토큰이다. 영어로
바꾸고 그 근거를 모듈 독스트링에 남겼다. 주석과 설명은 한국어를 유지한다.

### 최종 채점 (영어 프롬프트, k=5, T=0.6)

              문법 유효율   pass@5   개별 샘플
  fp32          100.0%      60.0%     18/50
  bf16          100.0%      70.0%     20/50
  (한글 프롬프트) 98.0%      40.0%     12/50
  미학습          60.0%       0.0%      0/20 (k=2)

bf16이 fp32보다 높게 나온 것은 표본 잡음이다(bf16이 더 좋을 수는 없다).
반대로 말하면 bf16 내보내기로 인한 품질 손실은 확인되지 않았다 —
export_weights.py가 주장만 하던 것을 처음으로 실측했다.

영어 프롬프트 3회 실측은 60% / 60% / 70% (개별 34% / 36% / 40%)로,
한글 24%와는 계속 벌어진다. 10문제 k=5는 재실행마다 한 문제씩 흔들리므로
세밀한 비교에는 못 쓴다.
